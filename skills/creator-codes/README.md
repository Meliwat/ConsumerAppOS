# creator-codes — why it works this way

Creator marketing is the distribution channel for small consumer apps: a creator posts about your app with their code, their audience types it in, and you pay the creator per subscription they brought. The infrastructure question is where the codes live and how a purchase gets tagged — and the usual answer is "a database and an API," which is exactly the kind of backend this OS refuses to own for a utility app.

## The whole backend is a JSON file

The codes list is a static `codes.json` on a Vercel site (one honesty note there: Vercel's Hobby tier is for non-commercial use, and an app that charges money isn't that — so it's the Pro plan, or any static host whose free tier permits commercial use; the files are identical either way). That sounds like a hack until you notice what a creator code actually is: public information. Creators post their codes on TikTok for a living — there is nothing to protect, no user data in the file, no write path to secure. A static file gives you free hosting, CDN caching, and a one-line workflow (edit the file, redeploy) with zero servers, zero auth, zero attack surface. The one non-obvious part is a tiny `vercel.json` that sets a CORS header on the file — without it, the app's fetch gets silently blocked and you'd spend an evening learning why.

The other half is attribution, and that's RevenueCat's job. The app attaches the entered code to the subscriber as an attribute, so it shows up on each customer's profile and — the part that matters for payouts — in RevenueCat's Scheduled Data Exports, where every purchase row carries the code and revenue-per-creator is a small spreadsheet exercise on data you already have. No database ever existed.

## Never block the doorway

The code screen sits inside onboarding, which means a network call sits inside the most fragile minute of the app's life. So the rule is absolute: the screen never waits for the network. If the codes list loaded, you get live feedback ("Supporting Sarah") as you type. If the network is slow, dead, or the site isn't deployed yet, your code is saved as *pending* and the flow moves on instantly — the app re-checks it on a later launch and upgrades it to valid (or not). Wrong codes don't block you either; they're saved, labeled unrecognized, and you keep moving. A *submitted* code is never dropped and a user is never stuck, which matters more than validating in real time. (Typing a code and then tapping Skip discards it — that's deliberate: Skip means skip.) One precision on "saved": the code lands instantly in a fast local shadow and becomes fully durable once the native storage write confirms — and if that write fails mid-launch, the app notices on the next start and retries it automatically, with the newest version of the record always winning. In the worst case — both storage layers unavailable — the save is honestly reported as memory-only, and the app keeps retrying the durable write during the session (quietly, in the background and whenever you next touch the screen). If the app is killed before any durable store accepts it, that code is lost; the design states that plainly instead of pretending durability it doesn't have.

Same honesty applies on the attribution side. The RevenueCat call that attaches the code doesn't confirm delivery on our bridge — so the app doesn't pretend it did. It records "attempted" and quietly re-asserts the attribute on every launch, which costs nothing and means a code that missed once lands eventually. In the browser preview the call no-ops with a note in the console, because there is no RevenueCat in a browser and faking it would teach you nothing.

## One line the curious will appreciate

This is the first skill that touches onboarding's `app.js` — two one-line splices that add the screen to the flow sequence. Every previous skill layered on top without touching it, and that restraint was the point; this one changes what the flow *is*, which no overlay can express. The precedent is deliberately narrow: flow changes edit the sequence, everything else stays an overlay.
