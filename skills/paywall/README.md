# paywall — why it works this way

The onboarding skill ships a paywall that is deliberately fake: placeholder prices, a banner that says so, a Restore button that politely admits it does nothing. This skill is the moment it becomes real — real App Store subscriptions, a real purchase sheet, a real entitlement that decides whether the app opens into the paywall or the shell.

## Why RevenueCat

You can talk to StoreKit directly, and for a hobby app that's fine right up until it isn't: receipt validation needs a server, entitlement state needs to survive reinstalls and family sharing and refunds, and Apple's edge cases multiply. RevenueCat is the boring, correct answer — it validates receipts server-side, owns the "is this person subscribed" question across devices, and gives you one dashboard for products, offerings, and revenue. The reference app in this repo ships it in production; this skill inherits its exact integration, down to the bridge quirks that only surface after a real launch (the configure call that isn't a promise and breaks everything if you treat it like one — that one cost a pre-launch debugging night).

Worth being precise about what the app does with that answer, because money code shouldn't hand-wave: on every launch that can reach RevenueCat, the app asks for a fresh answer about the one entitlement it gates on — it invalidates the SDK's cache first, so the verdict isn't yesterday's. A verified "yes" grants access; a verified "no" — an expired or refunded subscription — revokes it on the spot, and the next launch lands back on the paywall. When the check simply fails (offline, server hiccup), the app keeps whatever access you last verifiably had. It never punishes a network error, and it never revokes on a guess — and once the store has verifiably said "no," no stale local flag can sneak access back in.

## Why the preview mocks the whole flow

The rule of this OS is that the browser preview is the real app. But purchases are the one place where the real thing physically cannot run in a browser — there is no StoreKit, no App Store, no receipt. The choice was: let the paywall dead-end in the preview, or mock the entire flow so every step still walks. We mock it all: offerings load (with a visible label saying they're mock prices), the purchase button thinks for a moment and succeeds, the entitlement persists, the app routes to the shell on next launch. You can rehearse the complete business logic of your app — gate, purchase, restore, relaunch — before a single product exists anywhere. And the label rule is absolute: the mock banner comes off only when every price on screen came verified from Apple. The preview never manufactures a price it didn't get.

The mock world is strictly a browser thing. On a phone, if the purchase layer isn't set up yet — no key, broken SDK — the app says purchases aren't available and lets you retry. It never pretends a purchase succeeded on real hardware, because a fake "you're subscribed" on a device is a lie waiting to be shipped. Same discipline on trials: the button says "Start My Free Trial" only when Apple has verified this user is actually eligible for one; everyone else sees plain "Subscribe" and plain prices.

One more honest note: the paywall is soft. The ✕ in the corner really does skip into the app without paying — that's the onboarding design, kept deliberately. What the entitlement controls is where launches land and a persisted flag that later skills use to gate the features you decide are premium. If you want a hard paywall, that's a product decision you make on purpose, not a default this skill sneaks in.

## Why some steps are yours

Three things in this skill say "this step needs you at the keyboard," and it's not laziness. The Paid Applications agreement is a legal contract with banking and tax forms — no API signs it for you, by design. The RevenueCat dashboard setup is behind your login and involves handing RevenueCat an App Store key, which is exactly the kind of credential no agent should touch. What CAN be automated honestly, is: the subscription group and products get created through Apple's official API — names, durations, prices, the free trial — so the ASC clicking you'd normally slog through mostly disappears. The skill's job is to make the human steps small, exact, and one-time, and to do everything else itself.

One boundary worth understanding because it's the whole security model: the RevenueCat key that ships inside the app is the *public* one. It can fetch prices and start a purchase for your bundle id, and nothing else — the answer to "is this user subscribed" is computed on RevenueCat's servers from Apple's receipts. The secret keys (RevenueCat's `sk_`, Apple's `.p8`) live in dashboards and never enter the repo. If you remember one thing: `appl_` ships, everything else doesn't.

## Testing without waiting for Apple

A StoreKit configuration file rides along in the Xcode project: two test products that match what the API creates in App Store Connect. Run the app from Xcode and the real purchase sheet appears against those local products — no App Store Connect products, no sandbox account, no waiting on agreement processing. Two footnotes the skill is explicit about: RevenueCat needs its one-time dashboard setup either way (offerings come from its backend), plus a small certificate export from Xcode uploaded to RevenueCat so it can trust the local test transactions. The real lane — a sandbox Apple ID on a device against actual ASC products — is still the final word before shipping, and the skill is explicit about which claims each lane can and cannot prove.
